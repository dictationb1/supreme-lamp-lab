# R2 — a single WebSocket connection blocks the entire HTTP server (confirm; fix deferred)

- **Class:** real application backend defect (Windows PowerShell 5.1 server). This is very likely the **primary root cause** of the user's reported §6 UI problem (rendered UI, stale green "Live", missing FQDN/user/IP, "Launch unavailable", inactive controls).
- **Baseline:** complete unmodified clone at `4a91c5c2eadc12e5b071bc46bae7683087f56fbd`, `payloads/ghrdp-server.ps1`.
- **First causal failure (source-confirmed, HIGH confidence):** the accept loop is a single thread:
  ```
  while ($listener.Pending()) {
      $client = $listener.AcceptTcpClient()
      if ($client) { Invoke-ClientRequest -Client $client -Token $script:Token }   # synchronous
  }
  ```
  `Invoke-ClientRequest` handles `GET /ws` by calling `Invoke-F99WebSocketUpgrade` **inline** (line ~2434). That function enters a `while` loop that lives up to `$script:F99WsMaxLifetimeSec = 1800` seconds (30 min) or `$script:F99WsIdleTimeoutSec = 90` seconds of idle (line ~536). While it runs, the accept thread cannot drain any other connection, so **every** unrelated lightweight endpoint (`/health`, `/api/config`, `/api/native-status`, `/api/progress`, `/ping`) stalls in the TCP backlog.
- **Why it matches the reported UI:** the dashboard's `useDashboardPolling` opens a `/ws` socket once `/health` advertises `ws=true` (which the pinned source always does). The first `/ws` connection pins the single accept thread; from that instant the app's own config/native-status/progress polls never get answers, so the UI keeps its initial or cached data — a stale "Live" badge, blank FQDN/user/IP, a launch gate that stays disabled, and controls whose clicks never produce a backend effect. This is a *transport starvation*, not eight independent UI bugs.
- **Behavioural evidence:** lab run `40063545799` (real server on the client VM) hung for 26+ minutes in the measurement step as soon as a real browser opened the app — consistent with the 30-minute inline WS lifetime. The step could not be cancelled (the automation token lacks `actions:write`); it was bounded by the job timeout. Step logs/artifacts are not retrievable from this sandbox, so the hang is corroborated by source structure + timing, not by a raw stack trace.
- **Bounded re-measurement (this bundle):** `scripts/candidate/real-backend.js :: measureWsBlock()` opens **one** authenticated `/ws` upgrade, fires `GET /health` on a separate connection ~1.5s later, records whether it is blocked, then destroys the socket so the server recovers. The whole probe is hard-bounded to ~7s. Its verdict is recorded as `backend.ws_accept_loop_block` and is reported as a FAIL finding, never collapsed into a pass. The browser phase stubs WebSocket (recorded as `browserWsStubbed=true`) so the remaining controls can still be exercised against the real server without a 30-minute freeze.
- **Why NOT fixed in this session (honest boundary):** the correct repair is to serve each client on a background runspace/thread pool (or handle the WS pump on its own thread) so the accept loop keeps draining. That touches the socket/stream lifetime, `$script:` shared state, the F99/F101 WS keepalive and the audit writer across a ~9,800-line PowerShell 5.1 file, and this environment has **no local PowerShell interpreter** — it can only be validated through slow client-VM runs (one blocked at 26 min). A rushed async rewrite could silently break audit/logon evidence or leak sockets. It is therefore recorded as a confirmed, high-severity defect with a precise repair location, and left for a dedicated Windows-verification session. The task's requirement that "one slow request must not block unrelated lightweight endpoints" is **not** met by the current candidate.
- **Recommended bounded repair (for the next session):** dispatch `Invoke-ClientRequest` (or at minimum the `/ws` branch) to a `[runspacefactory]::CreateRunspacePool` worker (min 2, max ~16) with the accepted `TcpClient`/stream handed to the worker; keep the accept loop to accept+enqueue only; add a semaphore so concurrent writers serialize the audit log; add an invariant regression that a `/health` request returns while a `/ws` connection is open. Verify on the client VM with `measureWsBlock()` flipping from FAIL to PASS.
- **Confidence:** HIGH for the structural defect and its UI consequences (source + timing); the numeric block duration is measured on the VM by the bounded probe. The fix itself is NOT_RUN.
