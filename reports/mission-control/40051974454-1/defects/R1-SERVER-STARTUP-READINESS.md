# R1 — synchronous startup scans stall the HTTP server before the accept loop

- **Class:** real application backend defect (Windows PowerShell 5.1 server).
- **Baseline:** complete unmodified clone at `4a91c5c2eadc12e5b071bc46bae7683087f56fbd`, file `payloads/ghrdp-server.ps1`.
- **Symptom (historical + source-supported):** a TCP connection to port 7331 sometimes succeeds without an HTTP reply; readiness times out. The listening socket owner/cause was never conclusively proven on the live host.
- **First causal failure (source-confirmed):** the server calls `$listener.Start()`, writes the `LISTENING` marker to `server-ok.txt`, THEN runs three synchronous `Get-WinEvent` scans (`Update-RdpLogonAuthLast`, `Update-RdpConnLog`, `Update-RdpListenerTelescope`) on the *same thread*, and only AFTER those enter the `while ($listener.Pending())` accept loop. During the scans the kernel accepts TCP connections into the backlog but no thread drains them, so `/health` cannot answer. The 30s/30s/60s ticks re-run the same scans inline on the accept thread, so even after startup one slow request can block unrelated lightweight endpoints. The source's own comment names this as the deferred "F45-B isolated-scan-worker" work package.
- **Root-cause confidence:** HIGH for the *structural* defect (three scans before the accept loop; inline scans in the loop) — directly read from the pinned source and pinned by a static invariant regression. The *magnitude* is load-dependent (bounded `-MaxEvents` + `StartTime` queries over Security/System logs) and is MEASURED for real on the Windows client VM by `.github/workflows/real-backend.yml` → `scripts/candidate/real-backend.js` (baseline vs patched `connect → first /health` latency, plus `/health` sampling across a lab-shortened telescope tick and a concurrent inline-scan request). That measurement, not this static claim, decides the confirmed numeric stall.
- **Repair (bounded, PS 5.1-safe, no audit loss):**
  1. Remove the three synchronous pre-accept-loop startup scans. The F28/F30/F37 collectors are unchanged and remain the ONLY writers of their state files, running on the existing bounded ticks — evidence collection is preserved, only its first stamp moves to the first tick. An absent first stamp is reported honestly by `/health` as `scanTs=null` ("not reported yet"), never fabricated.
  2. Publish HTTP readiness via `server-ready.txt`, written from INSIDE the accept loop on its first iteration, so a consumer can wait for a service that has actually begun accepting instead of trusting a bind-only `LISTENING` marker.
  3. Bound the residual inline cost to **one** scan per iteration via a due-flag `if/elseif/elseif` chain, so coincident tick timers cannot stack two `Get-WinEvent` walks into one blocking stretch. A due-but-deferred collector runs on the next 50ms iteration.
  4. Keep every event query bounded (`-MaxEvents`, `StartTime`) and keep the honest `probeError`/`scanTs` unavailable path.
- **Not attempted (tracked as F45-B):** relocating the collectors to a fully isolated background worker/runspace. That would move several interdependent functions and cannot be proven safe without more Windows verification cycles than this bundle ran; it is explicitly NOT claimed as fixed.
- **Regression:** `src/tests/smoke/r1-server-readiness.test.ts` — 3 tests: no synchronous scanner invocation before the accept loop; `server-ready.txt` stamped from inside the loop; one-scan-per-iteration guard present. Fails 3/3 on the pristine baseline, passes 3/3 on the candidate. Static by necessity (the Linux CI lane has no PowerShell); the behavioural timing is proven on Windows by the real-backend job.
- **Confirmation:** clean-clone replay (`replay-candidate.sh`) reproduces the baseline failure, applies both ordered patches, matches candidate tree `62679b8edfde8ba2180f8bb3ca86c03e00d02b31`, and passes 1,378 smoke tests + production build. The definitive Windows backend timing is real-backend job `40068292422` / head `704fc5d0e7c525dd9fd1d9dc7079f21c95d91b04`: `connect → first /health` fell from **3474 ms baseline to 841 ms patched** (2633 ms / ~76% reduction). Only the patched label published `server-ready.txt` (`READY pid=7932 port=7331 …`); both listening sockets were owned by the real `powershell.exe` process (baseline pid 5428, patched pid 7932). See `evidence/real-backend-40068292422/comparison.json`, both label reports, `patched-server-ready.txt`, and the server stdout/stderr snapshots. Run `40067304717` (3225→719 ms) is retained only as corroboration. R1 does **not** fix the separate R2 inline-WebSocket accept-loop stall.
- **Patch:** `../app-patches/0002-R1-server-startup-readiness.patch`.
